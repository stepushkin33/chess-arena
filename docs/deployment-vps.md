# Деплой на свой домен

Подготовлена схема для одного VPS: Caddy раздаёт сборку React, принимает HTTPS и
передаёт `/ws` в Nest. Клиент использует тот же домен для страницы и WebSocket,
поэтому в браузерную сборку не нужно зашивать IP или отдельный адрес API.

```text
Браузер → https://ваш-домен → Caddy :443 → статические файлы /srv
                               └─────→ /ws и /health → Nest :3000
```

## Подготовка сервера

Нужен VPS с Docker Engine и Docker Compose v2.24.4 или новее (локальный override использует
`!override`). Домен должен иметь A-запись на IPv4 VPS. AAAA добавляйте только при наличии
рабочего IPv6. Откройте входящие TCP 80/443; UDP 443 нужен для HTTP/3, но не для работы игры.
Порт Nest наружу не публикуется.

Скопируйте исходники проекта на сервер и подготовьте окружение:

```bash
cp .env.example .env
```

В `.env` задайте настоящие значения:

```dotenv
DOMAIN=chess.your-domain.com
TLS_EMAIL=you@your-domain.com
```

Запуск из корня проекта:

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 server web
curl -f https://chess.your-domain.com/health
```

Ожидаемый ответ проверки — `{"status":"ok"}`. Откройте сайт, создайте комнату и
проверьте приглашение во втором браузере/на телефоне. В Network должна быть успешная
WebSocket-сессия `wss://chess.your-domain.com/ws` со статусом 101.

[Caddy получает и продлевает сертификаты автоматически](https://caddyserver.com/docs/automatic-https),
когда DNS и доступ снаружи настроены. Данные сертификатов лежат в Docker volumes
`caddy_data`/`caddy_config`; сохраняйте их при обновлениях.

## Локальная проверка production-образов

После запуска Docker на компьютере, с заполненным `.env`:

```bash
docker compose -f compose.yaml -f compose.local.yaml config --quiet
docker compose -f compose.yaml -f compose.local.yaml up -d --build
```

Откройте `http://localhost:8080`. Для этой проверки применяется отдельный Caddyfile
без HTTPS. Остановка именно этой конфигурации:

```bash
docker compose -f compose.yaml -f compose.local.yaml down
```

## Что собрано в проекте

- Multi-stage `Dockerfile`: сборка через `npm ci`, отдельные targets `server` и `web`.
- Nest запускается обычным Node от непривилегированного пользователя, без dev-transpiler.
- Healthcheck, корректное завершение по сигналам, автоматический рестарт контейнеров.
- WebSocket ping/pong удаляет зависшие подключения после потери сети.
- Проверка WebSocket Origin, ограничение размера кадра 8 КБ, лимит 60 команд за 10 секунд
  на соединение. Доступные Origin в production заданы явно.
- Прямые ссылки `/room/...` возвращают React entrypoint. Хешированные JS/CSS кешируются
  надолго, HTML проверяется заново, SVG-фигуры доставляются локально с того же домена.
- Базовые заголовки безопасности. [WebSocket Upgrade обрабатывает Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).
- GitHub Actions проверяет форматирование, lint, тесты, сборку, реальный WebSocket smoke
  и сборку обоих Docker targets. Workflow не выкладывает приложение автоматически.

## Обновление и эксплуатация

После обновления исходников:

```bash
docker compose up -d --build
docker compose logs --tail=100 server web
```

В текущей версии комнаты и гостевой счёт находятся в памяти одного Nest-процесса.
Перезапуск/обновление сбрасывает их и прерывает активные партии. Планируйте обновление,
когда нет игроков. Не запускайте несколько реплик Nest за балансировщиком: комнаты
между ними пока не разделяются. Для постоянной истории и горизонтального масштабирования
следующий шаг — PostgreSQL/Redis и восстановление сессий через серверные токены.

При обычном разрыве сети клиент переподключается и пытается войти в ту же комнату,
если она ещё существует и место не занято. Гарантированного резервирования места на
время отключения нет. Гостевой ID не является аккаунтом или средством аутентификации.

Публикация на реальном домене требует DNS и доступа к VPS. Эта задача подготавливает
исходники и конфигурацию; сертификат и внешний доступ проверяются уже на сервере.
